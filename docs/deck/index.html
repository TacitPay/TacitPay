TacitPay

Settlement anyone can verify. Numbers only you can read.

TacitPay is a protocol for private invoicing and settlement on Midnight. Get paid on-chain without publishing your books.

github.com/TacitPay/TacitPay · Apache-2.0

02 / 12 The problem

A public ledger publishes your income, your rates, and your customer list.

Settle an invoice in a stablecoin on a transparent chain and you permanently publish who paid whom and how much. Address clustering does the rest: your entire revenue history and counterparty list, readable by anyone, forever.

That is true whether you are a company, a two-person studio, a freelancer or an autonomous agent. Publishing your rate card to every competitor is not a side effect anyone signed up for — so most people settle in stablecoins reluctantly, or not at all.

The obvious fix does not work. Fully anonymous payment cannot be shown to an accountant, an auditor, a lender, or a counterparty in a dispute. It is unusable for anyone who has to account for their income — which is nearly everyone.

03 / 12 Why now

Midnight is the first chain where both halves are possible at once.

  • A dual ledger: a public state for what must be verifiable, a shielded state for what must not be seen. Not an overlay — the protocol's own design.
  • Zswap hides amount and owner at the value layer, so settlement itself is private without a mixer.
  • Compact makes disclosure explicit. A value reaches the public ledger only through a disclose() the author had to write.
  • Wallets now prove in the browser. The privacy story no longer requires the user to run infrastructure.

Wave 1 targets shielded tNIGHT and bridged tUSDM on Preview. The contract is token-agnostic — the payment token is fixed at deploy.

Midnight is Cardano's first partner chain, so it inherits the security of a large, mature network rather than bootstrapping its own.

04 / 12 The product

One invoice, four moves.

Step Who What reaches the chain
Create Issuer A random id, a hiding commitment, a status flag, an expiry
Send Issuer → payer Nothing. The payload lives in the URL fragment, which browsers never send to a server
Pay Payer A shielded coin and a proof that it matches the commitment
Withdraw Issuer A status change, proven from a secret only they hold

It is not a merchant app. The protocol knows two roles — whoever issued an invoice and whoever paid it — and nothing about who fills them.

05 / 12 Privacy model

What a chain observer actually sees.

Invoice record, as stored on the public ledger

id  31b40d47…c91b5d
amount  1,250,000
memo  Consulting retainer, Q3
issuer  merchant public key
payer  payer public key
status  OPEN
expires  none

The commitment is hiding, so amount and memo are inputs to it and never appear beside it. The owner and payer tags are per-invoice hashes — two invoices from the same issuer share no public value. Anyone can confirm this invoice settled; nobody learns the trade behind it.

Eleven invariants, INV-1 to INV-11, each mapped to the test that enforces it in docs/PRIVACY.md.

06 / 12 Architecture

Four layers, and a boundary that is the whole design.

Layer Holds Why there
Public ledger Invoice map, escrow, counters So anyone can verify existence and status
Zswap shielded The payment coin Amount and owner hidden by the protocol itself
Private state
(device, encrypted)		 Secrets, invoice bodies, salts, memos Witness inputs for proofs; never transmitted
URL fragment The invoice link payload Issuer to payer only — no server is in the path

Every circuit call goes through one library. The web app, the CLI, and Wave 2's SDK and MCP server all use it, so there is exactly one code path that decides what gets disclosed — and exactly one thing to audit.

07 / 12 The contract

Four circuits. Eleven disclosures, all deliberate.

Circuit Asserts Discloses
createInvoice id unused, amount > 0 id, owner tag, expiry (3)
payInvoice OPEN, unexpired, commitment matches preimage, coin colour and value payer tag, status, escrowed coin (4)
withdraw PAID, caller's secret derives the stored owner tag status (1)
cancelInvoice OPEN, caller's secret derives the stored owner tag status (1)

Ownership is proven from the witness secret, never from ownPublicKey(). That value is supplied by the prover, so it can name a recipient but cannot authorise anything. Getting this backwards is the bug that would let anyone withdraw anyone's money.

The coin-handling circuits run in the pure-JS runtime, so the contract can be verified with no Docker, no wallet and no network.

  • U-17 runs a full lifecycle, serialises the public ledger, and asserts the amount is absent in four encodings — along with the memo, the salt, both secrets and both parties' Zswap keys.
  • The integration test asserts the issuer's shielded balance increases after withdrawal. A status flag proves state changed; a balance proves value moved.
10 / 12 Roadmap

Three waves, each shipping something a judge can run.

Wave Theme Ships
1 The loop works Contract, tests, library, CLI, web app, Variant A escrow, judge sandbox
2 Developers and agents Variant B escrow, milestone escrow, claim-based refunds, recurring invoices, Node SDK, MCP server, tUSDM
3 Prove it to the auditor ZK revenue and receivables proofs, USDM on mainnet (stretch), mobile PWA

Stated openly: Variant A escrow publishes the coin's value — and its nonce — while the contract holds it. Test U-17b pins that exposure so it stays a tracked limitation rather than an assumption. Variant B closes it in Wave 2.

11 / 12 Market & distribution

The people already paid in stablecoins, and the software about to be.

Who needs it first. Freelancers, studios, agencies and suppliers who invoice across borders and already settle in stablecoins — the people for whom a public ledger is a live commercial problem, not a theoretical one.

How it spreads. The library is the product surface. Wave 2 ships it as an npm SDK and an MCP server, so an agent can issue and settle an invoice the same way a person does — and agent-to-agent payment has no privacy story at all today.

Adoption path: judge sandbox → self-serve web app → SDK in someone else's product → agents transacting without a human in the loop.
